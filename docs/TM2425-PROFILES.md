# TM2425 平台性能模式证据

调查日期：2026-10-18。适用范围仅为 `XIAOMI / TM2425 / REDMI Book Pro 16 2026`、BIOS `RMAPT6B0P0909`。本次只分析导出的 ACPI 表和官网下载包；没有执行性能模式切换、睡眠、关机、固件更新或物理内存写入。

## 证据身份与复现

本机导出物位于 `build/tm2425-acpi/`，未纳入源码。以下摘要只包含固件公共逻辑，不包含序列号等个人信息。

| --- | ---: | --- |
| 本机 `DSDT.aml` | 219166 | `9d34f503a282bfc53acffbf9a52ca7dd0c76e84c66dadfadb4c32f7ebbcde074` |
| 本机 `SSDT24.aml` | 12207 | `2541cae40164b5951adecf27c8b09122bc3dc4bad84c5ea61045f18371d9ebe8` |

分析器为 ACPICA `iasl 20251212`。逐文件运行 `iasl -d DSDT.aml`、`iasl -d SSDT24.aml`，本文行号对应默认输出的 `DSDT.dsl` 和 `SSDT24.dsl`。这些行号不依赖输出目录，但后续工具版本改变时应重新核对。不能直接以 `iasl -da` 合并全部表：本机部分 CPU SSDT 存在同名对象，会导致 `AE_ALREADY_EXISTS`，这是本次工具处理限制。

官方来源：[TM2425 下载页](https://www.mi.com/service/notebook/drivers/TM2425)，[精确 BIOS 下载包](https://cdn.cnbj1.fds.api.mi-img.com/mibook-drivers/BIOS/N5657SR/20260605/RMAPT6B0P0909.zip)。ZIP 的 REA 安全提取记录为 `ev_11ca8cd3de4cfe4e0d76fd4d61bc84daad327ac87f95cb6733923afe1074cdb8`，提取的 EXE SHA-256 为 `c682bb1aa466941226abce3b2dbdbb748df9f11e94b75351d18e10f8e4385436`。此 Evidence 只证明 ZIP 成员身份和提取，不声称 REA 反编译过 AML。

EXE 是受保护的 Insyde 7-Zip SFX：偏移 `0x3c1d53` 起的 payload 对每个字节旋转右移一位后恢复 7z。这与 [BIOSUtilities 的 Insyde 提取逻辑](https://github.com/platomav/BIOSUtilities/blob/main/biosutilities/insyde_ifd_extract.py) 一致。由 7-Zip 静态解包，使用 [UEFIExtract A75](https://github.com/LongSoft/UEFITool/releases/tag/A75) 提取固件表，没有执行 Windows EXE。UEFIExtract 对整个更新封装报告了对齐、区域和校验相关告警；因此没有把该封装当作可以直接刷写的完整 SPI 镜像。

官方 `XMCC1806` 与本机 `SSDT24` 等长，逐字节比较只有 11 处差异：表校验字节 `0x09`；OEM ID 的末尾填充 `0x0e..0x0f`；`XGNS` 动态地址/长度占位 `0x3bc..0x3bf`、`0x3c1..0x3c4`。其他字节完全相同，包括以下完整 `WMAA` 逻辑。这提供了本机导出与精确版本官方包的交叉验证。

## 本机固件已证明的协议

`SSDT24.dsl:141..143` 的 `_WDG` 将 GUID `B60BFB48-3E5B-49E4-A0E9-8CFFE1B3434B` 映射到 `AA` 方法块；`WMAA` 定义从 `371` 行开始，方法号为 1。

32 字节请求和回复的字段以小端存储。`SSDT24.dsl:373..387` 明确定义了偏移：

| 整体字节偏移 | 请求 | 回复 | 当前 C 结构中的回复位置 |
| --- | --- | --- | --- |
| 0..1 | `FUN1`，GET=`0xfa00`、SET=`0xfb00` | `SGER`，成功=`0x8000`，未知功能=`0xe000` | `reserved1`, `operation` |
| 2..3 | `FUN2`，功能号放在高字节 | `FUTR`，GET 通常回显功能 | `reserved2`, `function` |
| 4..5 | `FUN3`，子功能或模式 | `FRD0`，模式或回显子功能 | `data[0..1]` |
| 6..9 | `FUN4` | `FRD1` | `data[2..5]` |
| 10..13 | — | `FRD2` | `data[6..9]` |
| 14..17 | — | `FRD3` | `data[10..13]` |

### 获取与设置性能模式

GET：

```text
00 fa 00 08 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

成功回复：

```text
00 80 00 08 mm 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

`mm` 可为 `02`、`03`、`04`、`09`、`0a`。`SSDT24.dsl:398..423` 从 `FUNR(0x16)` 获取模式；`DSDT.dsl:22843..22849` 证明其返回 EC `QFAN`。GET 的 09 分支还调用 `NTDP` 更新热策略通知，因此这里的“GET”不是完全无副作用的纯函数；本次没有调用它做实验。

SET 是把 GET 请求中的 `fa` 换成 `fb`，把 `mm` 写入整体字节 4，其他字节保持 0。`SSDT24.dsl:693..715` 证明 `02/03/04/09/0a` 都有明确分支：清除 `SMMT` 与 `SMMD`，更新 `QFAN`，发送模式事件。`05..08` 也存在，但修改的是特殊策略字段；本项目没有足够理由暴露这些模式。

**SET 回复不能要求功能号回显为 08。** `SSDT24.dsl:654..719` 的 SET 分支只设置 `SGER=0x8000`，没有写 `FUTR`，因此正常回复是 `00 80 00 00` 加 28 个零。并且成功状态赋值位于所有分支之后，单独检查 `0x8000` 不能证明任意输入已经应用；调用者只应发出已经验证支持的模式值。若需要实测应用结果，应由明确授权的测试执行 SET 后再读 GET，本次没有实施这种测试。

### 高性能能力查询

原驱动的 GET 功能 19 (`0x1300`) **不在此固件的 GET switch 中**，会走 `SSDT24.dsl:641..643` 的 `0xe000` 分支。它不能用来要求传统圆口电源。

正确的本机功能是 GET 16 (`0x1000`)，子功能 3：

```text
00 fa 00 10 03 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

成功回复：

```text
00 80 00 10 03 00 vv 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

这里 `vv` 代表标志占位：当 EC `ADPW >= 0x64` 时返回 **0**，否则返回 **1**。证据为 `SSDT24.dsl:576..588`。必须从 `get_unaligned_le32(&result.data[2])` 取值，不能从 `data[0]` 取值，因为 `data[0..1]` 是回显子功能 3。子功能 6 会在同一 `FRD1` 字段直接返回 `ADPW`（`628..634` 行）。

已证明的是 `ADPW` 数值门限和标志方向；将它解释为 100 W 电源能力是变量用途及上游讨论支持的解释，不是 AML 单独给出的单位声明。SET 分支自身没有执行这个门限检查，因此“切换最高性能前要求系统外接电源，且能力标志为 0”属于保守的驱动策略，不能表述为已经观察到固件拒绝了电池上的写入。

## Linux 档位归并：证据与设计选择

本机 `DSDT.dsl:22870..22907` 的 `NTDP` 对热策略变量 `ODV1` 的映射为：

| 固件值 | `ODV1` | 本机直接证明 |
| --- | --- | --- |
| 02 | 2 | 与 0a 使用同一热策略编号 |
| 03 | 1 | 与 09 使用不同热策略编号 |
| 04 | 4 | 独立热策略编号 |
| 09 | 0 | 默认/自动策略编号 |
| 0a | 2 | 与 02 使用同一热策略编号 |

这些是模式编号和策略关系的静态证据，**AML 中没有 Quiet、Turbo、Eco 等人类名称**。本次检查官方 PCManager 5.8.0.74 提取物，找到性能模块和内部枚举名称，但未追通 Windows 内部枚举到此 WMI wire 值的转换，因此不以字符串或内部枚举数字充当机型映射证明。

一个相关的[上游作者实机补丁](https://lkml.iu.edu/2608.3/05526.html)把 **TM2424** 的值称为 Quiet=02、Turbo=03、Full-speed=04、Auto=09、Eco=0a，并采用三档归并。它与本机的编号集合及热策略关系吻合，但该补丁的实测机型和 BIOS 均不同，不能单独证明 TM2425 的名称或功耗。这也是不能将 03 随意称为“balanced”的原因。

本项目可采用如下 **Linux API 设计选择**，并将它严格限制到已核对的 DMI 和 BIOS：

| Linux 档位 | SET 的规范值 | GET 接受的值 |
| --- | --- | --- |
| `low-power` | 0a | 02、0a |
| `balanced` | 09 | 09 |
| `performance` | 04 | 03、04 |

09 不应称为 `balanced-performance`：没有证据证明它代表比 balanced 更高的性能。也不必因为它是固件自动策略就暴露为 `custom`；这里 `balanced` 是 Linux 提供给用户的归并策略。03 和 04 归入同一 Linux 档位意味着普通档位恢复可能把原始 03 写成规范值 04；若必须保持精确原始模式，睡眠保存/恢复应独立保存有效 wire 值，而非只存合并后的 Linux enum。尤其当最高档能力查询失败时，不能把模式 03 误改成 04。

所有未知模式、失败状态、错误的 GET 功能回显、错误的子功能回显和非 0/1 能力标志应报错，不应猜测默认值。已有“查询失败不阻塞睡眠”容错仍应保留。对于其他机型保留原行为；没有证据支持用这个表覆盖所有 Redmi 或所有 Bitland。

## 未验证边界

- 本次没有实测切换后的功耗、风扇行为或 Windows UI 标签。
- 未实测电池或低功率适配器上的 SET 拒绝行为。
- 没有证明未来 BIOS 使用相同协议；新 BIOS 需重新导出和核对。
- 没有把其他机型的功耗数字、SET fallback 或硬件能力直接移植到 TM2425。
